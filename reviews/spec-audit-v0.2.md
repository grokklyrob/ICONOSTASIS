## Executive summary

architecture.md v0.2 is largely implementable against browser, Web Audio, WebGL2/WebGPU, OPFS, and Nostr primary sources. Settled AMDs for async arrival (AMD-01), hybrid GEN (AMD-07), SecretRef (AMD-06), device tiers (AMD-03), and dual-emit Nostr (AMD-09) are **not** primary-source-infeasible as written; challenges on queue residency, PNA naming, CSP “session rebuild,” and MediaRecorder determinism were **dropped** as under-specification or preference.

**Eleven defects survive.** The only **critical** item is §13.1’s claim that **hosted-pair works from `file://`**: modern opaque `file:` origins + CORS-not-HTTP make automatic sibling `.icx` fetch non-portable. That cascades to a **high** M3 acceptance-line defect (§18: default hosted-pair + open from `file://` on a phone). A second **high** defect is §12.3’s generic high-entropy taint gate, which would block required content-hash / provenance digest strings.

Medium defects cluster in three areas: (1) **WCAG wording** — flash limiter approximates SC 2.3.1 rather than enforcing it; “accessible text track” is HTML media-element terminology misapplied to canvas captions; (2) **WebGL2 floor vs HDR** — float color-renderability needs `EXT_color_buffer_float`, not core WebGL2; (3) **§14.3 media** — uploads do not yield NIP-94 events; NIP-96 is registry-unrecommended and not hash-interchangeable with Blossom under default transforms. One **low** defect: Anthropic browser-direct is org/ZDR-conditional.

No AMD is overturned wholesale. Surviving work is **wording, qualification, and packaging contracts**—especially export/`file://`, taint-gate scope, and Blossom-first media.

## Ranked defects

### [critical] F-13-01 - hosted-pair cannot load sibling `.icx` under `file://` opaque origins
- **Spec:** §13.1; §18 M3; AMD-08
- **Claim:** Hosting is trivially static and works from `file://` for hosted-pair (`player.html` + `experience.icx` traveling together), including M3 demo export opened from `file://`.
- **Evidence:** WHATWG URL §4.7 Origin, scheme `"file"`: “Unfortunate as it is, this is left as an exercise to the reader. When in doubt, return a new opaque origin.” MDN CORSRequestNotHttp: CORS requests may only use HTTP(S); many browsers treat local files as opaque origins so sibling local resource loads yield CORS errors. Relative fetch of companion `.icx` from `player.html` on `file://` is therefore not a portable static path.
- **AMD:** AMD-08 (profiles remain feasible); the normative “works from `file://`” for automatic sibling load is defective.
- **Proposed edit:** Restrict automatic sibling `.icx` load to `http(s)` / `blob` / same-origin server contexts. For `file://` (opaque-origin documents), require **offline-complete** single artifact **or** explicit user file pick of the `.icx` after opening player (no silent relative fetch). Rephrase §13.1 “works from `file://`” accordingly; keep hosted-pair as static HTTP(S) pair.

### [high] F-13-03 - M3 demo `file://` on phone conflicts with default hosted-pair
- **Spec:** §18 M3; §13.1; AMD-20; AMD-08
- **Claim:** M3 acceptance: Via Lucis end-to-end, exported (hosted-pair default; offline-complete within cap…), opened from `file://` on a phone (`wayside`).
- **Evidence:** Same opaque-origin/CORS local-file rules as F-13-01. Default export is hosted-pair (companion load). The demo line does not name offline-complete for the phone `file://` path, so the natural “default export + `file://` on wayside phone” reading is platform-infeasible.
- **AMD:** AMD-20 / AMD-08 — profiles themselves OK; acceptance criterion defective as written.
- **Proposed edit:** Rewrite M3 demo to a feasible matrix, e.g.: (A) hosted-pair over `http(s)` on wayside phone; **and** (B) offline-complete (document-embedded) from `file://` on desktop evergreen; optional (C) player on `https` + user-picked `.icx` via file input on phone. Do not require default hosted-pair auto-load from `file://` on iOS/Android Safari.

### [high] F-12-01 - Generic high-entropy taint gate rejects required hash fields
- **Spec:** §12.3; also §12.2, §12.4, Appendix B
- **Claim:** Every serialize/export/publish path must reject the write if any string matches a generic high-entropy detector (in addition to `sk-`/`sk-ant-` and exact Vault strings), as a loud blocking error.
- **Evidence:** Same chapter requires content-hash asset identity and provenance digests (`artifactHash`, `promptHash`, `assets[].sha256`). MDN SubtleCrypto.digest: a digest is a short fixed-length value; SHA-256 is commonly hex-encoded. FIPS 180-4 §6.2: SHA-256 result is a 256-bit message digest. Hex/base64 encodings of uniform 256-bit digests are opaque high-entropy strings; a whole-serialization generic entropy rejector matches legitimate required fields and blocks conforming non-empty `.icx` writes.
- **AMD:** none (internal hard-requirement conflict)
- **Proposed edit:** Drop bare “generic high-entropy detector” as a whole-string rejector. Normative detectors: (1) known provider key prefixes/formats (`sk-`, `sk-ant-`, explicit allowlisted patterns); (2) exact equality against current Vault secret strings. Explicitly exclude structured content-addressing fields and non-string zip members. Any optional entropy heuristic must be scoped so it cannot reject required digests.

### [medium] F-8-02 - Flash limiter does not enforce WCAG 2.3.1 as claimed
- **Spec:** §16.4; AMD-10; §8.2 FX/ToneMap
- **Claim:** A flash limiter at the ToneMap stage (always on in the player) enforces WCAG 2.3.1 by counting whole-frame mean-luminance flashes (threshold-crossing peaks) over a rolling 1s window (≤3 flashes/sec) plus a max rise-rate damper.
- **Evidence:** WCAG 2.2 SC 2.3.1: pages must not flash more than three times in any one second, **or** the flash is below the **general flash and red flash thresholds** (opposing relative-luminance changes ≥10% max with darker <0.80; area vs ~10° field; separate saturated-red path). §16.4/AMD-10 use whole-frame mean peaks + rise-rate only — implementable control ≠ SC enforcement (over-suppress small bright spikes; under-detect localized/red flashes).
- **AMD:** AMD-10 (damper mechanism OK; **false “enforces WCAG” wording** is the defect)
- **Proposed edit:** Either (A) rephrase to “WCAG 2.3.1-oriented runtime damper” and document the approximation, or (B) require general/red flash threshold measurement with 3 flashes/s cap, keeping rise-rate as an additional non-WCAG control. Retain always-on-in-player.

### [medium] F-8-03 - Required HDR render targets are not core WebGL2 (acceptance floor)
- **Spec:** §8.1 Required capabilities; AMD-13; §16.3
- **Claim:** Required capabilities include HDR render targets; WebGL2 is the acceptance backend (floor); WebGPU used when present, never required.
- **Evidence:** Khronos `EXT_color_buffer_float`: only when enabled do R16F/RG16F/RGBA16F/R32F/RG32F/RGBA32F/R11F_G11F_B10F become color-renderable framebuffer attachments. WebGL 2.0 notes that RGBA16F requires `EXT_color_buffer_float`. Core WebGL2 does not mandate float color-renderability. On a conforming WebGL2 context without the extension, the required capability set cannot be satisfied while WebGPU remains never-required.
- **AMD:** AMD-13
- **Proposed edit:** Either (A) require `EXT_color_buffer_float` (or half-float equivalent) as a hard probe for HDR intermediates and document LDR (RGBA8) multi-pass fallback when absent, or (B) make “HDR render targets” conditional on float color-buffer support with documented quality drop. Align golden-frame notes for HDR vs LDR paths.

### [medium] F-10-02 - “Accessible text track” implies HTML TextTrack, which requires a media element
- **Spec:** §16.4; §10.1 captions / LIT/Caption
- **Claim:** all captions available as an accessible text track
- **Evidence:** WHATWG HTML: the `track` element / TextTrack model is for **media elements** only (`audio`/`video`). ICONOSTASIS captions are story-driven (`story.json` Caption[] + LIT/Caption) over a WebGL/WebGPU canvas player, not an HTMLMediaElement timeline. No standard way to attach a normative HTML TextTrack to a canvas-only presentation without hosting a media element.
- **AMD:** none
- **Proposed edit:** Replace “accessible text track” with a concrete player a11y contract, e.g. synchronized screen-reader-accessible DOM surface (or `aria-live` / off-canvas caption list) mirroring active cues; optional WebVTT export for recorded video separate. Keep keyboard-operable chrome and WCAG AA contrast.

### [medium] F-12-02 - Asset path model contradicts content-hash filenames
- **Spec:** §12.2; Appendix B
- **Claim:** `.icx` assets listed with human filenames (`seraph.bin`, `icon_station3.png`, `antiphon_2.ogg`) while the same section states assets are “referenced by content-hash filenames” / “asset references are by content hash”; Appendix B shows `path: "assets/seraph.bin"` + separate `sha256`.
- **Evidence:** Internal binding-text conflict: stable human basenames + path+sha256 sidecar vs hash-as-filename. Implementers cannot satisfy both literal readings without inventing dual addressing the spec never defines.
- **AMD:** none
- **Proposed edit:** Pick one normative addressing model. Recommended: keep human-readable (or stable) paths under `assets/`; require every asset reference to include a content hash (manifest `sha256` and/or graph refs by hash); optional content-hash filenames as packaging optimization only. Fix the tree comment.

### [medium] F-14-01 - Uploads do not yield NIP-94 events as stated
- **Spec:** §14.3 Media first
- **Claim:** Each upload yields hash-addressed URLs + NIP-94 file-metadata events.
- **Evidence:** Blossom BUD-02 returns only a Blob Descriptor JSON (`url`, `sha256`, `size`, `type`, `uploaded`) — not kind:1063. NIP-96 returns a partial HTTP `nip94_event` object missing id/pubkey/created_at/sig; client may **optionally** generate and send a full NIP-94 to relays after upload. NIP-94 defines kind:1063 as a separate signed relay event.
- **AMD:** none
- **Proposed edit:** Each successful upload yields a hash-addressed download URL (+ hash/size/type metadata). Optionally, the Publisher may construct and publish separate NIP-94 kind:1063 events; this is not produced by the media server. Map Blossom Blob Descriptor and NIP-96 response fields explicitly.

### [medium] F-14-02 - NIP-96 co-equal path is officially unrecommended and API-inequivalent to Blossom
- **Spec:** §14.3; §18 M4
- **Claim:** Media hosts are Blossom and/or NIP-96 as interchangeable first-class options; M4 lists Blossom/NIP-96 without distinction.
- **Evidence:** Official NIPs index marks NIP-96 unrecommended (“replaced by Blossom”); NIP-96.md deprecated in favor of NIP-B7. Wire formats differ: Blossom BUD-02 PUT `/upload` raw binary + BUD-11 kind:24242 auth with required `x` tags; NIP-96 POST multipart + NIP-98 kind:27235. Peer `and/or` under-specifies two full clients and contradicts registry status.
- **AMD:** none
- **Proposed edit:** Make Blossom (NIP-B7 + BUD-01/02/11, optional multi-server BUDs) the v1/M4 media path. If NIP-96 is retained, label legacy/unrecommended with a separate adapter contract; do not present as peer-equivalent in the M4 demo line.

### [medium] F-14-03 - Hash-addressed content guarantee fails under default NIP-96 transforms
- **Spec:** §14.3; §20 risk 3
- **Claim:** Uploads yield hash-addressed URLs suitable for multi-mirror redundancy and sha256-tagged bundle/player media.
- **Evidence:** Blossom BUD-02: servers MUST NOT modify the blob and MUST hash exact received bytes. NIP-96 permits compression/transforms; URL/path identity is original-file hash (`ox`); served bytes may differ (`x` after transform); multi-server redundancy needs `no_transform` + client hash check. Default NIP-96 breaks “served bytes === URL hash” interchangeability assumed by §20.3 ≥2-mirrors posture.
- **AMD:** none
- **Proposed edit:** State that content-addressed multi-mirror (hash of served bytes === URL hash) requires Blossom or NIP-96 with `no_transform` plus client hash check. Prefer Blossom for the ≥2-mirrors default. Keep sha256 on bundle tags as verified content hash of uploaded bytes.

### [low] F-9-04 - Anthropic browser-direct is org-conditional; §9.3 overclaims universal browser CORS
- **Spec:** §9.3 anthropic adapter; §9.1.3 default direct when browser-compatible + probe
- **Claim:** Shipped anthropic adapter “Supports the documented browser-direct access header; streaming via SSE.”
- **Evidence:** Anthropic official ZDR exclusions: “Cross-Origin Resource Sharing (CORS): CORS is not supported for organizations with ZDR arrangements. To make API calls from browser-based applications, route requests through a backend proxy server.” Hybrid routing remains feasible; §9.3 reads as unconditional browser-direct support.
- **AMD:** AMD-07 (hybrid remains feasible; qualification defect only)
- **Proposed edit:** Qualify §9.3: browser-direct requires the documented browser-access path and is unavailable for ZDR (and any org where CORS is disabled); default routing must follow live probe of a real CORS preflight/response, not static adapter metadata alone. Document helper as required fallback for ZDR.

## Method

1. **Phase scope:** Subsystems §7–§14 (arrival/render/GEN/story/audio-input/project/export/publish), with cross-cites to §15–§20 and Appendix B as needed.
2. **Binding text:** architecture.md Draft v0.2 only; CHANGELOG AMD-01..20 treated as settled decisions.
3. **Primary sources only:** vendor docs, formal specs (WHATWG/W3C/Khronos/IETF), official NIPs/BUDs, library primary docs. Blogs/tutorials excluded.
4. **Challenge bar:** overturn or defect a settled claim only with evidence it is **infeasible or false as written**—not preference, style, or “should be tighter.”
5. **Skeptic fail-closed on drops:** findings that amount to under-specification, optional implementation strategies, or wording polish without primary-source contradiction were **dropped**. Surviving items retain implementability of the *intent* where possible but record defective normative wording or self-defeating requirements.
6. **Synthesis:** no new findings invented; ranking by severity critical → high → medium → low; counts: survived=11, dropped=10, capped_out=0.
